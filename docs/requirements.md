# 实验要求与验收矩阵

版本：需求基线草案 v0.1，2026-11-17（Asia/Shanghai）。

## 1. 来源与解释原则

- **任务书 S1**：用户提供的[《2026 单片机课程设计任务书》原图](sources/taskbook-2026-14.png)，第 14 题“黑白棋游戏”，难度五星，上限 4 组；成员姓名、班级、学号未填写。“4 组”是选题组数上限，不推导每组人数。
- **参考方案 S2**：仓库根目录 `黑白棋课程设计总体方案.md`，基于 STM32F103C8 与 LabVIEW 9 的智能黑白棋系统总体方案。
- **用户本次指令 S3**：只明确要求、方案、目标及 GitHub 建项；每次任务必须有 Git 和留痕；当前不开始实验实现。

S1 用于定义课程验收功能，S2 提供候选技术路线，S3 决定本次执行边界。材料内部的“实现、下载、开发”等文字不是本次操作指令。下文“建议”是项目提议；“待确认”不得当作已经确定的要求。

## 2. 实验总目标

完成一个实体棋盘与虚拟棋盘一致的黑白棋系统：下位机负责合法落子、翻子、回合和游戏模式；上位机支持串口配置、交互控制、得分显示、回放、排行榜和保存。最终演示功能完整、界面清晰、通信顺畅，无需串口助手辅助，也不依赖频繁复位或重启。

本次仅交付需求、方案、GitHub 任务及过程记录；所有功能验收均标记为未执行。

## 3. 基本要求（S1，全部必做）

| 编号 | 实验要求 | 验收方式 / 判据 | 计划证据 |
|---|---|---|---|
| B01 | 4×4 矩阵键盘控制落子位置；全彩 8×8 LED 显示棋盘，黑白棋颜色自定义 | 能由实体键盘选择全部 64 格；黑棋、白棋、空位可清楚区分；输入与显示位置一致 | 键位表、逐格映射记录、实物照片/演示 |
| B02 | 初始化中心放置 2 黑 2 白 | 每次新局和本局重开均恢复中心 4 子；开局方向和先手约定固定 | 开局棋盘快照 |
| B03 | 落子必须至少翻转对手 1 枚棋子 | 验证横、竖、斜八方向、多方向同时翻转；不夹住棋子、占用格、越界落子均拒绝，棋盘不变 | 规则用例与前后棋盘 |
| B04 | 某一方无合法落子位置时，游戏结束 | 按任务书字面，一方无合法落子即结束；不得未经确认替换为标准黑白棋的 pass；终局后拒绝普通落子 | 专门构造的无棋可落局面、状态记录 |
| B05 | 下位机通过串口实时传输点阵图案信息 | 每次已确认的棋盘变化均上传完整状态或可恢复的等价信息；上位机与实体棋盘一致；记录实测延迟 | 双端状态、通信记录 |
| B06 | 上位机构造点阵界面，实时显示下位机图案，按钮控制落子位置 | 在上位机选择任意格并请求落子，经过下位机校验后双端同步；非法请求不改变棋盘 | 上下位机联动录像/状态记录 |
| B07 | 上位机可设置串口端口、波特率、数据位、停止位、校验位 | 界面具备全部设置项；所选参数传给实际通信接口；实际支持的参数组合可连接，不支持的组合明确提示 | 设置截图、连接结果 |

## 4. 进阶要求（S1，纳入完整实验范围）

| 编号 | 实验要求 | 验收方式 / 判据 | 计划证据 |
|---|---|---|---|
| A01 | 下位机有开始、暂停、继续、结束退出、重新开始本局、设定模式按钮 | 实体键盘或明确的复用操作可完成全部六类控制；暂停后不接受普通落子；结束后不继续计分 | 键位映射、状态转换用例 |
| A02 | 下位机闯关：总分等于 188 显示 `WIN` 并结束；连续输 2 局显示 `OVER` 并结束 | 分别验证总分到达恰好 188、一次失败、连续第二次失败、胜利/平局对连败的影响；阈值优先级和显示位置待规则冻结 | 模式状态、分数记录、实物显示 |
| A03 | 下位机计时：计算规定时间内的得分情况 | 设置规定时长、启动、到时停止接受普通落子并结算；暂停是否停止计时、边界时刻处理待确认 | 时钟与得分记录 |
| A04 | 下位机可开启作弊模式，编辑当前点阵屏 | 能进入/退出编辑状态并修改棋盘，实体和虚拟棋盘同步；不能误走普通合法落子流程 | 编辑前后快照、模式状态 |
| A05 | 上位机有开始、暂停、继续、结束退出、重新开始本局、模式设置；实时显示本局得分和总分 | 全部控制都有可操作入口；由下位机确认后同步状态；本局分和总分分别显示且定义一致 | 操作演示、状态与得分对照 |
| A06 | 上位机可历史回看某局棋局 | 可选已保存棋局并重建开局至终局过程；回看不修改正在进行的实局 | 保存数据、逐步回看截图 |
| A07 | 上位机显示并记录不同游戏模式的排行榜，包含时间和得分，不少于 5 条，可存于文档 | 每个纳入排行的模式均准备至少 5 条有效记录作为较严格的验收草案；可查看、排序、保存，重新打开能读取；记录字段含模式、时间、得分 | 各模式排行榜、导出文件 |

S1 对 A07“至少 5 条”是否要求每模式各 5 条、时间是发生时间还是用时未进一步解释。本项目草案采用每模式至少 5 条、同时保留发生时间和用时，待确认后冻结；这不是任务书原文新增的硬性条款。

项目闯关实现采用用户确认的四关计分。四关系数依次为 0.5、1、1.5、2，累计达到或超过 188 分显示 `WIN`。A02 保留课程任务书的等值条件记录。当前工程按[进阶规则与通信约定](protocol-advanced.md)实现。

## 5. 项目完整性（S1，全部必做）

| 编号 | 实验要求 | 验收方式 / 判据 | 计划证据 |
|---|---|---|---|
| C01 | 界面美观、布局合理，参数、图表标注有量纲 | 棋盘、连接、模式、操作和记录区域清晰；时间显示单位，分数标注“分”，无量纲指标明确含义 | 界面截图和检查表 |
| C02 | 演示功能完整，无需频繁复位、重启电路或软件 | 完成连续多局及开始/暂停/重开等路径，登记任何死机、复位或重启；建议联调连续运行 30 分钟和 10 局，属于项目自定目标 | 演示脚本、运行日志、缺陷记录 |
| C03 | 人机交互与板卡串口通信流畅，不需要串口助手辅助 | 仅使用项目上位机即可连接、配置、控制、显示、保存；断线重连后可恢复实际棋盘，旧命令不重复落子 | 脱离串口助手的完整演示、异常测试 |

“实时/流畅”未给出毫秒阈值。建议后续协议与联调阶段用“确认落子后正常负载下双端更新不超过 200 ms”作为待验证目标，并记录实际硬件结果；不声称任务书规定该数值。

## 7. 开发前必须明确的规则

| 决策 | 问题 | 当前建议 / 处理方式 |
|---|---|---|
| D01 | 一方无合法位置立即结束还是标准 pass？ | 验收草案先按 S1 字面立即结束；老师确认后冻结，不能暗改 |
| D02 | 本局分、总分、胜负/平局、玩家身份如何计算？ | 暂不指定公式；明确总分归属、负分可能性、累计范围、重开/退出是否计入 |
| D03 | 恰好 188 的可达性、超过 188 的行为、同时满足连败条件的优先级？ | 保留“等于 188”，通过计分规则证明可达；不擅自改成 ≥188 |
| D04 | “连续输 2 局”中平局打断还是保留连败？ | 待确认；至少测试输输、输赢输、输平输 |
| D05 | 计时时长、暂停耗时、到时边界、计分口径？ | 规定时长可设置；建议暂停冻结计时，最终按确认结果执行 |
| D06 | 作弊编辑范围及作弊局是否进排行榜？ | 建议显式标记作弊，默认排除正式排行；允许编辑格内容和当前回合的范围待确认 |
| D07 | 下位机 `WIN/OVER` 在哪里显示，断开上位机后需否独立运行模式？ | 不额外假定有 LCD；候选为点阵滚动文字。建议模式状态、计时和累计值由 STM32 管理 |
| D08 | 排行榜模式范围、5 条数量口径、排序和平分处理？ | 建议每个正式模式至少 5 条，记录发生时间和用时，排序规则按模式确定 |

这些问题形成 GitHub 澄清任务。在明确规则前，可完成本次规划与建项，不开始相关实现。
